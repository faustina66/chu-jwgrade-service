# 新用户部署指南

这份指南只讲一种情况：服务器上还没有这个项目，用户第一次部署。

核心流程只有五步：

```text
打开云服务器网页终端 → 从 GitHub 下载 → 运行部署脚本 → 查看服务状态 → 测试推送
```

不需要手动创建配置文件，不需要手动创建 Python 环境，也不需要自己上传 `data/`。

正式开始之前还有一步准备工作（第零步：把服务器的门锁好）——这台机器马上要存你的
统一身份认证密码，值得先花几分钟。

## 开始前准备

你需要：

- 一台云服务器，**Ubuntu 22.04 及以上**或 **Debian 12 及以上**；
- 云服务器管理后台提供的 WebShell、远程终端或 VNC 终端；
- 本项目的 GitHub 仓库地址（下一步要 clone 它）；
- 自己的教务系统学号和密码；
- PushPlus token。

> **版本要求是硬的，不是建议。** 本项目需要 **Python 3.10+**，而 Ubuntu 20.04 自带 3.8、Debian 11 自带 3.9，都跑不起来。
> 部署脚本会在装依赖之前先检查一遍，版本不够会直接停下并告诉你换哪个镜像。

服务器还必须能够访问长安大学的认证和教务域名。如果日志提示“请连接校园网”或 IP 白名单拦截，说明服务器网络无法访问学校系统，继续重复部署也没有用。

## 第零步：先把服务器的门锁好

**这一步不是走过场。** 部署完成后，这台服务器上会存着你的**统一身份认证密码**——
那套密码同时管着图书馆、校园卡、选课和学籍。服务器被入侵等于密码泄露。

在放代码之前先做三件事：

1. **改用 SSH 密钥登录，然后关掉密码登录。**
   顺序很重要：先把公钥放进服务器的 `~/.ssh/authorized_keys`，
   **另开一个终端确认密钥能登录成功**，再关闭密码登录。
   不要先关掉当前会话，否则配错了只能靠云厂商控制台救回来。
2. **安全组只放行 22 端口。** 本程序**只发出站请求、不监听任何端口**，
   其它端口一律不用开——开了就是白白多一个攻击面。
3. **给云厂商控制台账号开启二次验证。**

## 第一步：进入服务器网页终端

登录云服务器管理后台，打开“WebShell”“远程终端”或“VNC 终端”，进入 root 命令行。

看到类似下面的提示，就说明已经进入服务器：

```text
root@服务器:~#
```

不需要再执行 `ssh`。只有云厂商没有网页终端时，才在自己电脑的 PowerShell 中备用执行：

```powershell
ssh root@服务器IP
```

## 第二步：下载项目

把命令里的仓库地址换成实际的 GitHub 地址：

```bash
apt-get update
apt-get install -y git
mkdir -p /opt
git clone https://github.com/你的用户名/你的仓库.git /opt/jwgrade
cd /opt/jwgrade
```

如果 `git clone` 提示仓库不存在或没有权限，先确认仓库地址正确，并确认仓库已经公开。

> **路径必须在 `/opt` 下面，不能放 `/home` 或 `/root`。**
> systemd 服务单元开了 `ProtectHome=true`，`/home`、`/root`、`/run/user`
> 对服务是完全不可见的。放错位置服务起不来，而报错只有一句
> `status=200/CHDIR`，很难联想到是路径问题。
> 部署脚本会直接拦住你并提示怎么搬。

## 第三步：运行部署脚本

```bash
bash deploy/setup.sh
```

脚本会依次询问三项内容：

1. 教务系统学号；
2. 教务系统密码；
3. PushPlus token。

输入密码和 token 时屏幕不会显示字符，这是正常现象。脚本会自动完成：

- 创建 `config.yaml`；
- 创建 Python 虚拟环境并安装依赖；
- 创建 `data/` 状态目录；
- 创建专用的 `jwgrade` 服务用户；
- 安装 systemd 服务；
- **真实登录一次教务系统**，确认账号和解析都正常；
- 检查通过后启动常驻监控。

不要连续重复运行部署脚本。首次检查会真实登录教务系统，反复运行会消耗登录额度。

### 密码打错了不要紧

**这是最常见的情况，脚本已经为它做好了准备。**

- 脚本会**当场再问你一遍密码**，最多重试三次，不需要重新执行任何命令；
- 重试用的是一份**临时配置副本**，正式的 `config.yaml` 从头到尾没被改过；
- 装完临时副本自动删除，登录保护回到日常的一天一次。

**能试几次**：一小时最多 3 次、一天封顶 9 次。脚本不会自动睡着等一小时；
三次用完会退出，等这个小时过去再重跑脚本即可。

三次都错就别硬猜了——去 <https://ids.chd.edu.cn> 网页版登一次确认密码，
比在终端里试快得多。

> **看到「需要图形验证码」或「账号已被锁定」时，不要去改密码。**
> 这两种情况**不代表密码错了**。先去网页版通过验证码、或等锁定自动解除，
> 然后重跑脚本、输入**原来的密码**。脚本可能仍然报退出码 20，
> 因为这类情况同样需要人工介入。

### 首次检查失败了怎么办

脚本会停下来、**不会启动服务、也不会登记开机自启**，并打印退出码：

| 退出码 | 含义 | 怎么办 |
|---|---|---|
| `20` | 登录被拒绝，需要人工处理：密码错误、验证码或账号临时锁定 | 先看终端上方的具体提示。密码错误时脚本会重新询问；验证码或锁定时**不要改密码**，按上面的说明处理 |
| `21` | 配置或运行环境有问题（含 Python 版本过低） | 照报错内容处理后重跑 |
| 其它 | 多半是页面解析问题 | 加 `--dump` 重跑一次保存原始 HTML 便于排查 |

> `--dump` **不要当成常规步骤**：存下来的 HTML 里有你的姓名、学号和全部成绩，
> 看完记得删掉。

「先测试、通过了再登记开机自启」这个顺序是刻意的。反过来的话，一次失败的部署
会留下「现在没起来、下次开机自己起来」的状态——而它一起来就是一次完整登录，
人还不在场。

## 第四步：检查服务

```bash
systemctl is-active jwgrade
journalctl -u jwgrade -n 30 --no-pager
```

正常结果应当包括：

```text
active
解析出 N 条成绩
下次检查：...
```

看到 `active` 且日志完成一轮成绩解析，就说明部署完成。

首次运行还会看到这样一行：

```text
首次运行，已建立基线：N 门课程（其中 N 门已出分），本次不推送
```

**「本次不推送」是正确行为，不是出错。** 首次运行只记录当前状态作为基线；
如果把已有的历史成绩全推一遍，你会一次收到几十条微信。
从下一轮开始，只有真正发生变化才会推送。

实时查看日志：

```bash
journalctl -u jwgrade -f
```

## 第五步：测试 PushPlus 和手机显示

部署成功后，建议发送一条虚构成绩消息，确认 PushPlus 通道和手机显示都正常：

```bash
cd /opt/jwgrade
bash tools/test_push.sh
```

这条测试消息只调用 PushPlus，不访问教务系统，也不会触发教务系统登录。它只发送一条样例成绩，收到微信消息就说明推送通道和页面显示基本正常。

脚本还会生成一份 HTML 预览：

```text
/opt/jwgrade/data/push-preview.html
```

如果 PushPlus 测试失败，先看终端中的错误提示和 PushPlus 后台发送记录，不要反复重启成绩监控服务。

## 装完了，然后呢

到这一步就不用管它了，出分会自己推微信。

之后想改轮询频率、查看变更历史、换教务密码、停掉或换服务器，都在 **[`operations.md`](operations.md)** 里。

有两件事值得现在就知道：

- **服务 `active` 但一直没消息是正常的**——没有变化就不推送；
- **不要为了确认它还活着就反复重启**。会话还在时重启是免费的，会话一旦过期，重启就等于一次认证，而你事先并不知道它死没死。
  想确认状态用 `systemctl is-active jwgrade`。

## 新用户不需要做的事

- 不需要把 `config.yaml` 上传到 GitHub；
- 不需要自己创建 `data/`；
- 不需要手动安装 Python 依赖；
- 不需要手动写 systemd 服务；
- 不需要上传私人笔记、成绩快照或 Cookie；
- 不需要为了检查状态反复重启服务。

## 备用方案：服务器上不了 GitHub

只有在服务器无法执行 `git clone` 时才需要这一节。先在自己电脑上下载并解压本项目，然后上传：

```powershell
scp -r .\jwgrade root@服务器IP:/opt/jwgrade
```

Linux 或 macOS 上把路径换成 `./jwgrade` 即可。上传完回到服务器执行：

```bash
cd /opt/jwgrade
bash deploy/setup.sh
```

**上传前确认你手上这份目录里没有 `config.yaml`、`data/` 或任何日志**，那些是运行后才产生的，不该跟着源码走。

## 已经部署过的服务器

如果服务器上已经存在 `/opt/jwgrade` 或 `jwgrade.service`，**不要照本指南重复执行**。

原来的 `config.yaml`、`data/` 和 `/etc/jwgrade.env` 都要保留——尤其是 `data/`，里面是你的成绩快照，丢了会被当成首次运行重建基线，**那期间出的分永远检测不出来**。

升级、改密码、换服务器这些都属于维护场景，步骤见 **[`operations.md`](operations.md)**。
